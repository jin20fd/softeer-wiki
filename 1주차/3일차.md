## WAS 1 - 1
1단계 기능 요구사항을 구현하면서 기존 RequestHandler의 역할을 RequestData, MessageParser, FileManager 클래스로 요청 처리를 분리하였다.  
이 과정에서 각 클래스의 의존성을 어떻게 잘 처리할 수 있을까에 대한 고민을 주로 하였다.

### 객체의 의존성
**두 객체를 미리 생성하여 RequestHandler의 생성자에 주입하는 방식으로 리팩토링하는 것이 좋을까?**

`RequestData`, `MessageParser`, `FileManager` 객체가 매 요청마다 새로 생성되어야 한다.  
현재는 이 객체들에 **`RequestHandler`** 가 의존하고 있다  
(= `RequestHandler` run 메서드 내부에서 객체를 생성한다)

- 현재 구조에서는 MessageParser의 생성자 인자인 BufferedReader의 값은 RequestHandler의 run메서드 실행 중에 알 수 있다.
- MessageParser의 생성자에서 RequestData 객체가 필요하다


의존성 주입에 대해서 학습해보았을 때, 기존 코드는 확실히 각 객체가 불필요한 의존성을 갖는다고 판단하였다. 코드의 흐름도 설명하기 어려웠다.  
그리고 MessageParser, FileManager는 메서드만으로 분리해도 무방하지 않을까 라는 생각이 들었다.  
그래서 두 객체의 불필요한 멤버 변수들을 없애서 생성자의 인자를 없애고, 객체를 미리 생성해둔 후에 필요한 값은 메서드의 인자로 받아서 **RequestHandler의 외부에서 주입**하는 방식으로 리팩토링 해보려고 한다.  

추가적으로, 요청마다 MessageParser, FileManager를 만드는 것이 아닌, 하나의 MessageParser, FileManager를 여러 요청에서 사용하면 concurrency 패키지를 활용해볼 수 있지 않을까라는 생각이 들었다


## 학습
### 의존성 주입
객체가 필요로 하는 다른 객체(의존성)를 외부에서 주입받아 사용하도록 하는 방식

구현 방법
- 생성자 주입 : 필요한 의존성을 모두 포함하는 클래스의 생성자를 만들고 그 생성자를 통해 의존성을 주입한다.
- Setter 주입 : 의존성을 입력받는 Setter 메소드를 만들고 이를 통해 의존성을 주입한다.

장점
- 단위 테스트에 편리하다

    모의 객체를 만들어 생성자에 주입하여 테스트코드를 작성할 수 있다
    
- 코드 가독성이 높아진다

# 회고
**Keep**

- 설계 후에 구현하기
    
    어제의 전반적인 과제에 대한 설계를 바탕으로 해야할 일을 세분화하여 계획하였다. 설계하면서 미리 고민을 해보아서 실제로 코드를 작성하면서 고민하는 시간이 줄었다고 느껴졌다. 설계를 하고 구현을 하여서 예상 소요 시간과 실제 소요 시간이 크게 차이나지 않았던 것 같다.
    

- 예상 소요 시간 산정하고, 실제 소요시간 측정하기
    
    각 계획에 대한 예상 소요시간을 작성해보고 실제 소요 시간도 작성해보았다. 그러다보니 할 일을 명확히 분리하고 더 구체적으로 계획을 세우는데에 도움이 되었다.
    
    실제 소요 시간은 정확하게 측정하기는 어렵긴했지만, 시작과 끝 시각을 확인하여 대략적으로 작업에 걸리는 시간을 확인하였다. 할 일을 수행하는 데에 얼마나 시간이 걸렸는지 체감하지 못하는 경우가 있었는데, 의식적으로 확인하다보니 스스로의 작업속도를 파악하는데에 도움이 되었다.
    

**Problem**

- 구현하면서 추가되는 할 일 관리가 되지 않았다
    
    구현하면서 추가적으로 구현하거나 학습하고 싶은 부분들이 생기면서 계획한 일보다 학습할 내용이 많아지는 문제가 발생하였다. 코어 타임 이후에 물리적으로 시간을 투자하여 해결하였지만 꾸준히 발생할 것 같은 문제여서 구체적인 해결방안(초기 계획을 여유롭게 산정하기, 추가로 구현하고 싶은 부분의 중요도 고민하기 등)을 마련해야 할 것 같다.
    

- 문서 작성(제출)을 미루게 되는 문제
    
    PR, 위키, 회고 등의 작성해야할 문서들이 있는데,  구현한 내용, 고민한 내용을 적으면서 작업하긴 했지만 작성한 내용을 정리해서 위키나 PR을 올리지는 못했다. 각 문서에 작성해야 할 내용이나 언제 작성할지에 대한 규칙을 마련해서 작성해야할 것 같다.
    

**Try**

- 계획 외의 추가로 구현하고 싶은 부분이 생기면 중요도 고려하기
    
    Problem에 작성한 것처럼 추가되는 할 일이 많아지면서 시간 관리가 어렵다고 느껴졌기 때문에, 계획 외에 하고 싶은 일이 생기면 이 일의 중요도를 고려해보고 시작하려고 한다.
    
- 문서 역할 분리하고 루틴 만들기
    
    문서가 체계적으로 나뉘지 않아서 작성(제출)을 미루게 되는 문제가 발생했다고 생각하였다. 그래서 각각의 문서의 규칙, 작성할 내용, 작성할 시간을 정해서 이에 따라서 작성해보려고 한다.
    
    - PR
        - 미션의 step별로 제출(이번주는 3회)
        - 하루에 여러개 올리지 않기(몰아서 작업하지 않기)
    - 회고
        - 평일 매일 필수 작성 - 다음날 10시 전에 작성하기
        - 당일 일과 끝난 이후 또는 다음날 아침 이동시간에 작성
    - 위키
        - 평일 매일 필수 작성 - 당일 잠들기 전에 정리하여 올리기
        - 하루 일과 진행중에 틈틈이 작성
