## 그룹 세션

### **파일 읽고 응답하는 방법**

- **`readAllBytes()` 활용 : 파일의 전체 내용을 한 번에 메모리로 불러오는 방식**
- **`ByteArrayOutputStream` 활용  : 버퍼 단위로 읽어와서 메모리에 저장**

`readAllBytes()` 함수로 구현하였는데, 다른 팀원분은 `ByteArrayOutputStream` 를 활용하여 구현한 것을 확인하였다. `ByteArrayOutputStream`은 버퍼 단위로 읽어오는 것을 확인하였고, `readAllBytes()`가 구현된 코드도 같이 확인해보았다.

실제 코드를 확인해보니 int의 최댓값이 넘는 크기의 파일이면 에러를 던지는 것을 확인할 수 있었다.

예외처리는 되어있긴 했지만, 패키지에서 가져와서 사용하는 함수도 잘 알아보고 개발해야 겠다고 반성하였다.

### RequestHandler 의존성 주입 리팩토링

어제 고민한 내용을 토대로 아래와 같이 생성자를 주입하도록 구현하였다.

**객체 생성 시점**

WebServer 실행 →  `ReqeustHandler`, `MessageParser`, `FileManager` 객체를 생성

새로운 요청 발생 → `ReqeustData` 객체 생성

**의존성 주입**

RequestHandler의 생성자에 `MessageParser`, `FileManager`, `ReqeustData`를 추가하여 주입

**+) 리팩토링 과정에서의 트러블슈팅**

첫번째 요청은 정상적으로 동작, 이후에는 잘못된 응답을 제공하는 문제가 발생하여 꽤나 헤메었다.

요청/응답 객체의 생성 위치를 잘못 작성했던 실수…

소켓에 클라이언트 요청이 올 때마다 생성해야 하는데 try-catch문과 while문을 착각하여 잘못 작성하였다.

### `final` 키워드 적용

변경 불가능하다는 의미를 가지고 있다

주로 클래스 필드에 관성적으로 사용해왔는데, 적용 예시와 언제 사용하면 좋은지 알아보았다.

**적용예시**

- 변수 : 할당된 값 변경 불가능
    - 참조형 변수(객체)의 경우 : 참조 값은 바꿀 수 있지만, 내부 값은 변경 가능하다
    - 클래스 내부 필드인 경우 : 생성자에서 필수적으로 초기화해야 한다
- 클래스 : 상속 불가능
- 메서드 : 오버라이드 불가능

찾아보다 [어떤 블로그](https://better-tomorrow-than-today.tistory.com/m/105)에서 [openjdk style guide](https://cr.openjdk.org/~alundblad/styleguide/index-v6.html)라는 것을 발견하여 직접 있어서 확인해보니 아래와 같은 내용을 포함하고 있었다.

<aside>

Method parameters and local variables should not be declared final unless it improves readability or documents an actual design decision.
메서드 매개 변수 및 로컬 변수는 가독성을 향상시키거나 실제 디자인 결정을 문서화하지 않는 한 final로 선언해서는 안 됩니다.
Fields should be declared final unless there is a compelling reason to make them mutable.
필드는 변경 가능하게 만들어야 할 설득력 있는 이유가 없는 한 final로 선언되어야 합니다

Making fields immutable where possible is good programming practice. Refer to *Effective Java, Item 15: Minimize Mutability*
for details.가능한 경우 필드를 변경할 수 없게 만드는 것이 좋은 프로그래밍 습관입니다. 자세한 내용은 *Effective Java, Item 15: Minimize Mutability*를 참조하십시오.

</aside>

이 가이드를 참고하여 클래스의 필드에서 변경할 필요가 없는 요소들은 final 키워드를 추가해주었다.

## WAS 1 - 2

### 응답을 위한 ResponseData 구현

요청 메시지 정보를 객체로 저장한 RequestData 처럼 응답 또한 객체로 정보를 관리하도록 구현하였다.

- **요청부터 응답까지의 전체적인 흐름**
    
    요청 메시지 파싱 → RequestData 에 정보 저장(메서드, 경로, 헤더 등) →요청 객체를 확인하여 전달할 정보를  ResponseData에 저장(응답코드/메시지, 바디 등) → 응답 메시지 생성 → 클라이언트에게 응답 전송
    
- **다양한 응답 형식 지원**
    
    html파일 형식만 서빙하던 기존 코드에서 다양한 파일 형식을 지원하기 위해 MIME 타입에 대해 학습하였다.
    
    확장자와 미디어타입 정보를 갖는 `ContentType` enum을 만들었다.
    
    요청 필드의 ContentType을 응답 객체에 저장하고 응답 메시지를 만들어 반환한다.
    

### **MIME 타입**

미디어 타입 (Multipurpose Internet Mail Extensions

문서, 파일 또는 바이트 집합의 성격과 형식을 나타낸다

| 문서 종류 | 확장자 | MIME 타입 |
| --- | --- | --- |
| HyperText Markup Language (HTML) | `.htm`, `.html` | `text/html` |
| 종속 스타일 시트 (CSS) | `.css` | `text/css` |
| JavaScript | `.js` | `text/javascript` |
| Icon format | `.ico` | `image/vnd.microsoft.icon` |
| Portable Network Graphics | `.png`  | `image/png` |
| JPEG 이미지 | `.jpeg`, `.jpg` | `image/jpeg` |

- [일반 MIME 타입 - HTTP | MDN](https://developer.mozilla.org/ko/docs/Web/HTTP/Guides/MIME_types/Common_types)

**Problem**

- 구현 계획을 모두 달성하지 못했다

개발 시간이 많아서 어제보다 많은 할 일을 계획했는데, 문서화에 생각보다 많은 시간을 써서 달성하지 못한 것 같다. 나름 체계를 갖추어가려고 하고있지만 시간이 많이 쓰이는 것 같다.

- 개발하며 발생한 에러의 원인을 AI의 도움을 받아 해결하였다

구현 도중 에러를 발견했고 원인을 찾는데에 오랜 시간이 소요되었다고 생각하여 AI에게 코드를 보여주고 해결하였다. 문제를 파악하고 해결하는 능력을 키우기 위해서는 스스로의 힘으로 찾아보는 연습을 해야할 것 같다.

**Try**

- AI 활용해서 문서화하기

문서화에 많은 시간이 소요되는 문제가 있었다. 위키에는 학습한 내용들과 구현 흐름을 작성하지만 PR에는 작업한 내용과 집중해서 개발한 내용 위주로 작성한다. 그래서 작성한 위키나 커밋을 바탕으로 PR을 AI의 도움을 받아 정리해보려고 한다.

- 문제 해결 시, AI 사용 기준을 세워 실천하기

스스로 해결하는 연습과 빠른 오류 해결 사이의 기준을 세워야 한다고 생각하였다. 최소 한 시간은 혼자, (가능하다면) 동료들과 함께 논의 이후에 AI를 활용하여 찾아보아야 겠다.
