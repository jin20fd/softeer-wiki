# 학습

### 중복 userId 처리 로직에 대한 테스트코드 작성

현재 데이터베이스는 userId를 key로 저장하기 때문에 기존 로직에서는 동일한 userId로 회원가입을 요청하면 사용자 정보가 덮어씌워지는 문제가 있었다. 그래서 먼저 회원가입한 사용자만 저장하는 로직을 추가하였다.

ConcurrentMap의 putIfAbsent 메서드를 사용하여 중복 회원가입을 방지하였다. 즉, 데이터베이스 수준에서 중복을 방지한다.

처음에는 테스트 코드를 작성할때 saveUser를 호출하는 스레드를 각각 만들고 실행시켜서 테스트하려고 하였다. 하지만 스레드의 실행 순서를 보장할 수는 없어서 우선 순차적으로 saveUser를 호출하는 경우에 대한 테스트 코드를 작성하였다.

→ 추후에 요청 순서 보장에 대해서 고민해보아도 재미있을 것 같다. 요청 큐 관리?

### test와 main의 데이터 공유

> 데이터베이스 클래스가 static이어서 테스트코드를 작성할 떄에도 Databse.db와 같이 불러서 사용할 수 있었다.
그래서 괜히 걱정이 생겼다. 혹시나 main함수를 실행하면서 테스트코드도 같이 실행하면 동일한 데이터베이스를 사용하게 되는 것은 아닐까?
> 

그래서 테스트함수와 메인함수를 실행할 때, `ManagementFactory.getRuntimeMXBean().getName();` 을 출력하여 확인해보았다.
main을 실행하면서 테스트코드를 실행해보니 서로 **다른 JVM에서 동작**하는 것을 확인할 수 있었다. 따라서 test와 main은 별도의 static 공간, 별도의 데이터베이스를 갖는다는 것을 알 수 있었다.

### 응답 메시지를 생성하는 ResponseHandler 분리

RequestHandler가 하는 역할이 너무 많은 것 같아서, 응답 메시지를 생성하는 역할을 하는 `ResponseHandler` 인터페이스를 만들고 제공하는 응답 메시지에 따른 구현체를 만들었다.

- `StaticFileResponseHandler`
    1. 정확히 일치하는 경로의 static 파일
    2. static 디렉터리의 index.html 파일
- `UserAPIResponseHandler` : /user/create → userManager의 반환값
