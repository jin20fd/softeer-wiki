### 작업 과정에서의 배운 점

- **RDS의 서브넷 그룹**
    
    RDS 인스턴스를 생성하는 과정에서 서브넷 그룹을 설정해야 하며, 서브넷 그룹은 서브넷이 포함된 가용영역이 2개 이상이어야 한다는 사실을 알게 되었다.
    
    처음엔 단일 AZ를 사용하도록 설정했음에도 불구하고 서로 다른 가용영역을 갖는 2개의 서브넷을 설정해주어야 하는 이유를 납득하지 못하였다. 심지어 두개의 서브넷 중에 어떤 서브넷에 인스턴스를 설정할 수도 없다고 한다.  우선 찾아본 바로는 다중 AZ로의 전환에 대비하고, 장애가 발생했을 경우에 AWS 내부에서 처리해주기 위해서 다른 AZ를 갖는 서브넷들의 그룹이 필요하다고 한다. 
    


# ⏳ 회고

### **Keep**

- **팀원들과 그룹 회고를 진행하면서 개선 사항들의 구체적인 해결방안 결정하기**
    
    회고를 진행하면서  스크럼, 회의, 회고 등의 여러 문서들을 관리해야 하는데 문서화의 체계화가 부족한 것 같다는 문제가 제시되었다. 이 문제를 해결하기 위해서 구체적인 해결방안을 결정하는 것이 좋을 것 같다고 제안하였고, 각 문서를 작성할 공간과 템플릿을 팀원들과 명확하게 이야기하여 분리하였다. 
    
- **사소한 트러블 이슈도 공유해보기**
    
    스쿼드 세션을 진행하면서 CICD 구축 과정에서의 github actions 이벤트 path 조건에 대한 이슈를 언급하였다. 크게 중요하지 않은 내용이라고 생각했고 원래는 이야기하지 않아도 될 부분이라고 생각했었는데, 명규님이 멀티모듈을 사용하는 자신의 팀에서는 해당 조건을 활용하면 큰 도움이 될 것 같다고 이야기를 해주셔서 이야기하기를 잘 했다고 생각하였다. 사소하다고 생각했던 이슈들도 시간이 된다면 많이 나누어보도록 해야겠다.
    

### **Problem**

- **문제 제기를 하는 것에 대해 망설인다**
    
    팀 내에서 작성하는 여러 문서의 관리 체계가 잡혀있지 않아서 불편함을 느끼고 있었다. 하지만 너무 사소한 부분으로 팀원들을 피곤하게 만드는 것은 아닐까라고 생각하여 이야기를 하지 않고 그냥 사용하였다. 회고를 하면서 감사하게도 민정님께서 이 부분에 대해서 먼저 이야기를 꺼내주셨고 다른 팀원들도 모두 불편함을 느끼고 있었다는 사실을 알게 되었다.
    

### **Try**

- **문제를 제시한다고 생각하기보다 팀원들의 의견을 가볍게 먼저 질문해보기**
    
    Problem에 적은 것처럼 사소하다고 느낄 수도 있는 맞추어나갈 부분들을 문제로 제시하는 것이 어렵다고 느껴졌다. 너무 딱딱하게 생각하지 않고, 가볍게 먼저 물어봐도 좋을 것 같다. 문제를 제시한다고 생각하기보다 상대방의 기준이 무엇인지를 먼저 물어보고 들어보면서 자연스럽게 맞추어 나아가야 겠다.
