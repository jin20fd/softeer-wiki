### 작업 과정에서의 배운 점

- **Builder 패턴에서 특정 필드를 설정하지 않으면, 그 필드는 기본값을 갖게 된다**
    
    **→ 기본값은 [자바의 필드 초기값 규칙](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html#jls-4.12.5)에 따라서 생성된다**
    
    builder패턴을 사용해서 entity를 설정하였는데, 따로 처리가 필요한 필드가 있어서 필드값을 설정하지 않고 entity를 생성하였다. 설정하지 않은 필드가 있어서 오류가 발생할 것이라고 예상하고, 코드를 실행하였는데, 필드의 값이 0으로 설정되어 데이터베이스에 들어가는 것을 확인할 수 있었다. 빌더 패턴에 대해서 부족한 이해를 가지고 사용했다는 점에서 반성하게 되었다.
    

- **Bean Validation의 트리거 시점(`@NotNull`, `@CreationTimestamp` 어노테이션)**
    
    Entity의 필드를 아래와 같이 작성하였고, 해당 entity를 DB에 저장하는 과정에서 ConstraintViolationException 이 발생하였다. 
    
    ```java
    @NotNull
    @CreationTimestamp
    @Column(name = "created_at", nullable = false, columnDefinition = "TIMESTAMP")
    private LocalDateTime createdAt;
    ```
    
    `@CreationTimestamp` 보다 Bean Validation 이 실행되는 시점이 빨라서 생기는 문제였고, 해당 entity에서는 유효성 검증이 필요없었기 때문에 @NotNull 필드를 제거해주어 해결하였다
    
    영속성 관련 개념이 부족해서 원인을 빨리 찾지 못했었던 것 같다. 해당 개념을 추후에 더 공부하고 보완해보도록 해야겠다.
    

### 어려웠던 점

- **에러 코드 관리 방법을 결정하는 것**
    
    아래와 같이 크게 두가지 중에 고민하였다.
    
    1. 도메인마다 별도의 에러 코드와 메시지를 전부 만들어서 관리
        
        장점 : 많은 예외를 모두 관리하는 것이 힘들다
        
        단점 : 사용자에게 구체적인 예외를 제공할 수 있다
        
    2. 공통 에러코드(해당 값은 존재하지 않습니다 등등,,)만을 선정하고 관리
        
        장점 : 새로운 예외 메시지를 생성할 필요가 없어서 관리가 크게 필요하지 않다
        
        단점 : DB를 조회해서 발견 가능한 예외들을 분기하기 어렵다
        
    
    팀원들과 논의한 결과 프론트에서는 확인할 수 없는 예외에 대한 상세한 메시지도 전달할 수 있도록 백엔드 측에 enum을 만들어서 도메인별 에러 코드 및 메시지를 모두 관리하도록 결정하였다.
    

# ⏳ 회고

### **Keep**

- **진행 상황이나 작은 트러블슈팅 메모하면서 개발하기**
    
    작업을 모두 마치고 위키를 작성하려고 하면 오늘은 뭐했더라…하고 고민하는 시간이 더 많았던 것 같다. 개발하며 마주한 작은 트러블 슈팅들을 간단하게라도 메모하였더니 학습 내용을 더 자세하게 작성할 수 있고 학습 의지를 키우는 데에도 도움이 되었다.
    
- **제대로 알고 사용하는지 검토하기**
    
    빌더패턴과 여러 어노테이션을 사용하는 과정에서 당연히 알고 있다고 생각하며 사용해왔지만, 동작원리를 이해하지 못한채 사용해왔다는 것을 인지하게 되었다. 이러한 문제를 인식하게된 점을 칭찬하고 싶다.
    

### **Problem**

- **생각한 것보다 작업 속도가 느리다**
    
    API 개발을 거의 처음 오늘 시작하였는데, 생각보다 오래 걸렸다. 예상한 것보다 적어도 두배의 시간이 걸렸다. API를 작성하며 맞추어야할 부분들(swagger 문서 형식, DTO의 네이밍, DTO를 class와 record 중 무엇을 사용할 것인지 등등,,)을 논의하면서 진행하다보니 더 오랜 시간이 걸린 것 같긴 하다.
    

### **Try**

- **예상 작업시간, 실제 소요시간 작성해보기**
    
    할일을 관리할 때에 원래도 사용하던 방식인데, 최근엔 함께하는 작업이 많아서 측정하지 못했던 것 같다. 이제 나름 분업을 하였으니 혼자 하는 작업에 대해서는 다시 예상 시간과 소요시간을 측정해보아야 겠다. 가능하다면 함께하는 작업에도 도입해보면 좋을 것 같다.
    
- **출퇴근 시간에 간단한 학습 진행 다시 시작하기**
    
    오늘 개발하면서 부족하다고 느낀 점들이 많았기 때문에, 이를 보완하기 위해 다시 출퇴근 시간에 간단하게 유튜브나 블로그를 읽으면서 학습을 진행해보아야 겠다.
